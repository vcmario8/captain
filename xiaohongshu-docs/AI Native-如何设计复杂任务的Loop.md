# AI Native —— 如何设计复杂任务的 Loop？

1. 什么是 Loop
LLM 已经足够聪明，可以胜任大量事务型工作，例如检索信息、整理材料、生成内容、编写代码和分析数据。但面对持续数小时甚至数天的复杂任务，仅靠模型能力仍然不够，因为这类任务通常需要多轮交互，并伴随需求补充、方案调整、执行失败、人工确认和结果返工。
如果一直沿用聊天式协作，历史对话和任务材料会不断累积。新旧结论混在一起，真正有效的信息被逐渐稀释；任务一旦中断，系统只能重新阅读历史对话来猜测当前进度；执行失败后，模型也容易停留在当前问题上反复尝试，而不知道应该回到哪个阶段修正前置条件。
Loop 就是为解决这些问题而设计的工程化任务运行机制。它把复杂任务从不断增长的对话流，重构为一组可以持久化、恢复、验证和回流的任务节点。LLM 负责节点内部的理解、推理和执行，Loop 则负责节点之间的状态推进、失败处理和人工决策。
因此，Loop 不是简单地让 LLM 多执行几轮，也不是给失败任务增加重试次数。它真正要做的是，把人与 LLM 在复杂任务中的多轮协作方式，编码成一套可以持续运行的任务系统。

2. 为什么需要 Loop
复杂任务的主要挑战，已经不是模型能不能完成某个单点动作，而是系统能不能让模型在较长时间内保持正确方向，持续推进，并在中断或失败后恢复。
可以把 Context 和 LLM 的关系类比为内存与 CPU。LLM 提供计算和推理能力，Context 提供本轮执行所需的工作集。CPU 不会永久保存程序状态，LLM 也不会在一次推理结束后自动记住任务进度。如果把全部历史对话、文档和执行产物持续塞进 Context，任务运行得越久，工作集就越大，最终会出现上下文爆炸、关键信息被淹没、过期结论继续生效，以及推理质量下降等问题。
Loop 的处理方式与操作系统管理任务相似：任务状态不依赖 LLM 的临时记忆，而是持久化到外部存储；每次执行只把当前阶段需要的最小工作集装入 Context；节点执行完成后，再把新的状态和产物写回外存。任务中断时，系统可以从最近的有效快照继续，而不需要回放整段聊天记录。
所以，Loop 解决的不是单次生成质量，而是复杂任务的持续执行能力。

3. loop 设计要点

3.1 任务拆解到图——有记忆的任务图
复杂任务首先要从一段连续对话，重构为一个可执行的任务图。正常执行路径可以用 DAG 表达：任务被拆成若干节点，节点之间通过依赖边连接，明确哪些步骤必须先完成、哪些步骤可以并行，以及哪些产物会成为后续节点的输入。
但只要系统允许失败后返回前置节点，整个结构就不再是严格的 DAG。更准确的说法是：正常路径由 DAG 描述，失败路径通过回流边形成 Loop，最终构成一个有状态的 Workflow Graph。
每个节点都需要明确自己的输入、动作、产物、准入条件、准出条件和失败规则。输入定义本节点执行所需的信息，动作说明 LLM、Skill 或工具具体做什么，产物定义执行完成后必须生成什么。准入条件决定节点何时可以开始，准出条件决定什么事实成立后才能进入下一节点，失败规则则说明执行失败后如何分类以及应该回到哪里。
这些定义把任务推进从“人在对话中临时指挥”，变成“系统按照任务图和状态规则运行”。

3.2 保存记忆：节点快照与 Checkpoint
任务图中的每个关键节点都对应一个进度快照，但快照不能只保存一段自然语言总结。一个可恢复的节点快照至少应包含三类结构化信息：节点产物、执行证据，以及状态和版本。
节点产物也就是 Artifact，可以是需求文档、分析结论、代码 Diff、测试报告、评审意见、数据结果或配置变更。执行证据包括节点使用了哪些输入、调用了哪些工具、产生了什么结果、验证是否通过，以及失败原因是什么。状态和版本则记录节点当前处于未开始、执行中、等待人工、已通过、失败还是已失效状态，并保存产物版本、完成时间和确认人等元信息。
这些状态和产物不能只存在于 LLM 的 Context 中，而应持久化到本地文件、数据库、对象存储、云文档或任务平台。任务恢复时，系统读取当前任务状态，定位最近的有效节点，加载该节点的有效产物，并重新构造当前节点所需的最小 Context，然后继续执行。
这就是 Loop 中的 Checkpoint 机制：恢复点是节点快照，恢复依据是外存中的状态和产物，而不是模型是否还“记得”此前的对话。

3.3 恢复记忆：按节点装载最小上下文
断点恢复不等于把全部历史重新塞给模型。每个节点都应该定义自己的 Context Contract，明确当前阶段必须加载哪些信息、哪些材料可以按需引用，以及哪些历史内容已经失效或不应继续继承。
例如，方案设计节点主要需要需求边界、存量约束、现有契约和候选方案，不需要加载所有执行日志。编码节点需要已经确认的技术方案、目标代码切片和契约变更，也不需要重新读取完整的需求讨论过程。测试节点则需要验收条件、代码变更、测试入口和预期结果，不需要携带多个已经被否决的方案草稿。
长文档、完整日志和全量代码 Diff 等大体积材料继续保留在外存中，以链接、路径或对象 ID 的形式存在。只有当当前节点确实需要某部分信息时，系统才读取对应章节、代码片段或日志窗口。
这样一来，Context 的规模主要取决于当前节点的任务复杂度，而不是整个任务已经运行了多久。上下文不会随着任务历史无限增长，模型也不需要在大量过期信息中重新判断哪些内容仍然有效。

3.4 失败回退——按失败类型智能回流
复杂任务中的失败不是异常情况，而是正常执行路径的一部分。测试会失败，方案可能被否，需求可能发生变化，外部依赖也可能暂时不可用。成熟的 Loop 不会让 Agent 在当前节点无限重试，而是先识别失败类型，再根据规则决定应该停留、重试还是回到前置节点。
LLM 可以负责读取错误现象、总结失败原因，并给出候选分类，例如需求信息缺失、方案不自洽、实现存在缺陷、测试暴露设计问题、执行环境不可用或外部依赖不稳定。但“应该回到哪个节点”不能完全交给模型自由决定，而应由预先定义的失败类型与回流节点映射规则控制。
例如，需求信息不足时应回到需求澄清节点，方案被否时应回到方案设计节点，测试发现实现问题时应回到编码节点，测试暴露设计问题时则应回到方案节点。环境故障不应该触发重新设计，而应该回到环境检查或等待节点。
这里必须区分重试和回流。重试是在输入和前置假设没有变化的情况下，重新执行当前节点；回流则表示系统发现问题来自前置产物或前置假设，需要返回上游节点重新生成。如果失败来自需求或方案，继续重试编码节点只会重复产生错误结果。

3.5 人参与关键决策
Loop 不是为了彻底消除人的参与，而是把人的介入集中到少数真正需要承担责任的节点。需求边界确认、共享契约变更、核心方案选择、风险接受、代码合入和最终发布等环节，通常具有较高风险或不可逆性，不适合完全由 Agent 自动决策。
系统运行到这些节点时，应暂停自动推进，生成结构化的 Human Gate 信息，让人能够看到当前背景、待审核产物、候选方案、Agent 推荐项、主要风险以及需要执行的动作。人的选择应收敛为 approve、reject、override 或 stop，并作为正式决策写回任务状态。
这种设计并不是增加审批流程，而是重新分配人的注意力。人不再陪着 Agent 完成每一个细节，而是在少量关键节点做价值判断、风险判断和责任确认。AI 负责连续执行，人负责关键决策。

3.6 回流后的产物失效
当任务回流到前置节点时，后续节点的产物不能继续默认有效。假设施工方案已经被修改，那么基于旧方案生成的代码、测试报告和评审结论都可能失去可信度。如果系统继续复用这些结果，新旧版本就会混在一起，最终造成上下文污染和链路不一致。
因此，每个 Artifact 都需要记录自己的生成节点、依赖的上游产物及其版本。当某个前置节点生成新版本后，系统应沿依赖关系将后续产物标记为失效。失效通常不等于物理删除，而是将产物标记为 deprecated 或 stale，以保留完整的审计历史。
后续节点再次执行时，只能读取当前有效版本。已经失效的产物可以用于回溯和复盘，但不能继续参与当前任务的推理和决策。
这套机制与构建系统的依赖失效很相似：上游输入发生变化，所有依赖旧输入的下游结果都需要重新生成或重新验证。它既避免了旧上下文污染，也保证了产物链路的一致性和可追溯性。

3.7 可重复执行——如何保证幂等
节点快照、版本失效和幂等解决的是不同问题。节点快照负责恢复任务，版本失效负责维护上下游一致性，而幂等负责控制重复执行对外部系统造成的副作用。
每个节点都应带有任务 ID、节点 ID、输入版本和执行版本。执行前，系统先判断同一组输入是否已经产生有效结果。纯推理节点通常可以安全重算，新结果以新版本保存；但写数据库、发送消息、提交代码和执行发布等副作用节点，需要额外设计幂等键、事务、状态检查或人工 Gate。
如果一个节点在执行过程中中断，系统还必须判断外部动作是否尚未发生、已经发生但状态尚未写入，还是只完成了一部分。只有明确副作用的真实状态后，才能决定重新执行、执行补偿，还是转交人工处理。
因此，Loop 可以为幂等提供任务状态和版本基础，但不能替代传统工程里的事务、幂等键和补偿机制。

4. Loop 最终解决了什么
Loop 首先解决了任务恢复问题。任务进度以节点快照形式保存在外存中，即使原来的对话已经结束，系统仍然可以从最近的有效节点继续运行。
其次，它控制了上下文规模。每次执行只加载当前节点需要的最小工作集，长文档、完整日志和历史产物继续留在外存中，按需读取，而不是全部进入 Context。
它还把失败和返工纳入了正式流程。系统先对失败进行分类，再回流到正确节点，避免 Agent 在错误阶段持续重试。上游节点发生变化后，下游产物会自动失效，从而保证版本一致性。
更重要的是，Loop 明确了人的责任边界。关键节点通过 Human Gate 暂停执行，人的决策被结构化记录，整个任务过程可以审计和追溯。
当任务阶段、准入条件、准出条件、失败类型、回流路径和人工决策点都被显式定义后，同类复杂任务就不再依赖某个人临场指挥，而可以复用同一套 Workflow。

5. 总结
Loop 的本质不是让 LLM 变得更聪明，而是为 LLM 建立一个可持续运行的复杂任务运行时。正常任务依赖由 DAG 表达，失败路径通过回流边形成 Workflow Graph；节点承担 Checkpoint，产物与状态保存在外存；每次执行只加载当前节点需要的最小 Context；任务依据 Condition 推进，失败依据规则回流；上游变化触发下游产物失效，而人在关键 Human Gate 承担决策责任。

最终，复杂任务从“人与 LLM 不断对话”，升级为一套可恢复、可验证、可回流、可审计的任务系统。
